# Cimba Code Review — Pre-Release-Candidate Assessment

**Subject:** Cimba — multithreaded discrete event simulation library in C
**Version reviewed:** 3.0.0-beta, `main` branch snapshot (zip commit `e40e114b50aa4d03d6e71c54e40588d8ae13b75c`, July 2026)
**Reviewer:** Claude (Anthropic), AI-assisted code review requested by the maintainer
**Date:** July 6, 2026
**Review environment:** Ubuntu 24.04 x86-64, GCC 13.3, Meson 1.11, NASM 2.16, single-vCPU container. Linux paths exercised at runtime; Windows port reviewed by inspection only.

## Scope and method

This is the fifth review in the series and the first full review since the June 10 baseline. It has three goals: verify that the defects reported in the June 10, 15, 17, and 18 reviews remain fixed in the current tree; assess the code added or reworked since then (the coroutine stack pool, the hash-map compaction, the error-recovery path, the install/packaging work, the stack-size API); and take a fresh adversarial pass over the process-interaction layer with emphasis on the interaction edges the earlier reviews identified as the library's historic weak spot — tied timestamps, timeouts, and out-of-band process control.

The review was build-and-run based. The tree was built in release and debug+ASan/UBSan configurations; the full test suite passes in release (23/23); the per-module unit tests were re-run under ASan+UBSan (clean, with one test-teardown caveat noted below); the staged `meson install` tree was verified self-contained by compiling every public header standalone in C11 mode out-of-tree; and **four reproduction programs were written and executed against the release and debug builds**. Findings marked **[verified]** were demonstrated by running code; findings marked **[by inspection]** follow from reading the source. The multithreaded end-to-end test (`test_cimba`) was confirmed passing in release; under ASan it ran correctly through 115+ trials but was not run to completion in this single-core container — the project's own CI covers that configuration with an appropriate timeout multiplier.

## Executive summary

The trajectory since June 10 is exactly what one wants to see in a pre-release hardening campaign. **Every one of the eighteen previously reported defects and essentially all of the polish items were verified fixed in this snapshot**, several of them with structural improvements rather than spot patches: the guard-key scheme is now carried on the awaitable, the hash map reclaims tombstones by in-place compaction, the installed headers are self-contained with a CI job that enforces it permanently, a pkg-config file is generated, the public headers consume cleanly from C11, the NASM objects now carry an explicit CET property note, and the new thread-local stack pool with per-size free lists eliminates the `mprotect` serialization on the hot path. The engine, the data structures, the numerics, and the build/CI infrastructure are in genuinely strong shape.

However, the fresh adversarial pass found **a new family of high-severity defects in the same neighborhood as the June 10 findings: stale wakeup events**. Every blocking primitive in Cimba resumes waiters through scheduled wakeup events, and none of those events validates on execution that the waiter is still in the wait the wakeup was issued for. Whenever a process leaves a wait through an out-of-band path — most importantly the **timeout idiom that the library's own test suite demonstrates** (`cmb_process_timer_add` followed by a blocking acquire) — an already-scheduled wakeup survives and later resumes the process spuriously inside whatever it is doing next. Three reproductions demonstrate, in the default release build and **silently even in the full debug+sanitizer build**: a `hold()` that returns immediately with `CMB_PROCESS_SUCCESS`, a cascading chain of corrupted timers, a waiting process stranded forever at a free resource (a lost-wakeup deadlock), and — through a related cleanup gap in `cmb_process_wait_event` — a **release-assert abort on a legitimate model** when a process is stopped after its awaited event fired at the same timestamp.

These are the same class of bug as June's F1/F3, one layer further out: the primitives now clean up their *queue entries* correctly, but not their *in-flight wakeups* or their *reverse registrations* (event waiter lists, process waiter lists), and an abandoned resource grant is never re-offered to the next waiter. Because timeouts and tied timestamps are bread-and-butter in real simulation models (reneging customers, deadline-driven jobs, integer-valued clocks), I would treat this family as the gate for 3.0. A single unifying mechanism — a per-process wait generation counter checked by every wakeup handler — would close the entire class; concrete fixes are proposed below. Everything else found in this pass is medium severity or lower.

## Status of previously reported findings

All re-checked in the current tree, by re-inspection and, where the original report was demonstrated by a reproduction, by re-testing the behavior:

- **F1 (guard hash keys)** — fixed. `cmb_resourceguard_wait` records the enqueue key on the awaitable (`guard_key`); cancel, remove, and `cmb_process_priority_set` all recover the entry through `cmi_process_guard_key`. Priority changes on queued waiters reshuffle the guard heap correctly. **[verified by inspection and exercised by the new repros]**
- **F2 (error-recovery corruption)** — fixed. The recovery branch calls `cmi_coroutine_reset_to_main()` (which also re-syncs ASan/TSan fiber state and, on Windows, re-adopts the TEB stack fields) and `cmi_event_queue_reset()`. The `__builtin_setjmp`/`__builtin_longjmp` design is well documented in `cmi_config.h`, including the `_FORTIFY_SOURCE` and Win64 SEH rationale.
- **F3 (binary resource double-grant)** — fixed. `cmb_resource_acquire` now refuses the fast path while the guard queue is non-empty and re-checks availability in a loop after every wakeup. (But see R1: the *stale wakeup itself* survives through a different door.)
- **F4 (NULL trial-function dispatch)** — fixed (`*(cimba_trial_func **)trial`).
- **F5 (header packaging)** — fixed properly: the required `cmi_*.h` headers are installed with a documented rationale in `include/meson.build`, a pkg-config file is generated, and a CI job (`test/tools/verify_install.sh`) compiles each public header standalone against the installed tree. Verified in this review by staging `meson install` and compiling all public headers out-of-tree in **C11** mode — all pass, confirming the `cmi_config.h` compatibility shim (`CMB_NORETURN`, `CMB_MAYBE_UNUSED`, `CMB_FILE_NAME`, C11 floor check) does its job for consumers.
- **F6 (guard comparator)** — fixed; now a valid strict weak ordering (priority, then arrival time, then key).
- **F7 (Windows TEB offset)** — fixed; all `DeallocationStack` references are `gs:0x1478`, on both the read and write sides and in the switch macros.
- **M1 (tombstone decay)** — fixed structurally: the hash-heap counts tombstones and `hashheap_compact` rebuilds the map in place when live+tombstones reach 75 % of the table, so lookups can no longer degrade over a long churn-heavy run.
- **M2–M8** — all fixed as recommended: preempt cancels the *victim's* awaiteds; interrupt of a dead process is check-and-warn; the logger mask and time formatter are process-global atomics; `cimba_trials_remaining` clamps; `format(printf, 5, 0)` and `CMB_ATTR_PRINTF` attributes are in place; `pthread_create`/`pthread_join` are checked; the guard-page teardown drops `PROT_EXEC`; coroutines carry a `pool_allocated` ownership flag so thread cleanup never frees an embedded struct at the wrong address.
- **N1–N4 (numerics)** — spot-checked present as described in the June 18 verification review (bounded `discrete_nonuniform`, weight-normalized `cmb_wtdsummary` moments, `p == 1` special cases, `fivenum` small-count guard). Not re-derived here.
- **Residual items from June 15/17/18** — the C23-consumer binding is resolved (shim, verified); the stack-size gap is resolved (`cmb_process_initialize_wssz`, `cmb_process_default_stacksize_set` with atomic access); `cmb_random_dice`/`cmb_random_loaded_dice` now compute the span in unsigned arithmetic with an explicit overflow assert; MXCSR preservation is default with `NMXCSR` confined to `benchopt`; the `pushfq`/`popfq` pair is gone from the Linux context switch; the NASM objects now *explicitly* emit a `GNU_PROPERTY_X86_FEATURE_1_AND = 0` note with a thorough comment documenting the CET posture, rather than merely lacking notes.

This is a clean sweep, and the quality of several fixes (compaction, install verification, the CET note, the recovery documentation) exceeds what was asked for.

## New verified defects

### R1 — Stale resource-guard wakeups: timeouts at tied timestamps cause spurious resumes, cascading timer corruption, and stranded waiters (HIGH) [verified]

When a guard grants the resource, `cmb_resourceguard_signal` dequeues the head waiter and schedules a `wakeup_event_resource(pp, CMB_PROCESS_SUCCESS)` event at the current time. If, at that same timestamp, the waiter is resumed first by any other means — canonically its own timeout timer, which was scheduled earlier and therefore carries a lower FIFO key and **always executes before the just-scheduled grant** — the waiter leaves `cmb_resourceguard_wait` with `CMB_PROCESS_TIMEOUT`. The wait correctly cancels its queue entry (already dequeued, a no-op) and its awaitable, but **nothing cancels the already-scheduled SUCCESS wakeup**, and **the abandoned grant is never re-offered** to the next waiter.

*Repro (`repro_a_stale_grant.c`, provided):* H holds resource R for 5 time units; W arms a 5-unit timeout (`cmb_process_timer_add(me, 5.0, CMB_PROCESS_TIMEOUT)`, the exact idiom used in the project's own `test_resourceguard.c`) and calls `cmb_resource_acquire`; W2 queues behind W. Observed in the default release build, and **identically, with no assert firing, in the full debug + ASan/UBSan build**:

1. W's acquire returns TIMEOUT at t=5 — correct so far.
2. W's next `cmb_process_hold(10.0)` **returns immediately at t=5 with signal `CMB_PROCESS_SUCCESS`** — the stale grant resumed it.
3. Because that hold "succeeded", it does not cancel its own timer; that orphaned timer then fires at t=15 and **cuts W's subsequent 20-unit hold short at 10 units, again with signal SUCCESS** — the corruption cascades from one wait to the next, each spurious wakeup planting the seed of the following one.
4. W2 — behind a now *free* resource — **is never woken and stays queued forever**; the simulation drains and ends with W2 still `RUNNING`. In a model where W2's activity feeds the rest of the system, this is a deadlock; in a queueing study it silently deletes a customer.

Note the reach of this: every blocking primitive in the library waits through the same guard machinery (`cmb_resource`, `cmb_resourcepool`, `cmb_buffer`, `cmb_objectqueue`, `cmb_condition`), so the stale-grant mechanism applies to all of them, and tied timestamps are not exotic — any model with integer-valued or discretized times produces them constantly. The pool/buffer recheck loops make the *primitive itself* tolerant of a spurious SUCCESS arriving inside its own wait, but the spurious wakeup lands wherever the process happens to be suspended *next*, which is usually somewhere else entirely.

**Fix:** see "Closing the stale-wakeup class" below. The minimal per-primitive repair is: on leaving `cmb_resourceguard_wait` with `sig != CMB_PROCESS_SUCCESS`, pattern-cancel any pending `wakeup_event_resource` targeting the caller, and if a cancelled one carried a SUCCESS grant, call `cmb_resourceguard_signal` on the guard so the grant passes to the next eligible waiter. The re-signal is also needed in `cmb_resourceguard_cancel`/`cmi_resourceguard_remove_key` (used by interrupt/stop paths) whenever the removed waiter *could* have been granted — otherwise stop/cancel of a head waiter at a free resource strands those behind it the same way.

### R2 — `cmb_process_wait_event` leaves both of its registrations behind on a timeout: spurious wakeup when the event fires, and a release-assert abort when combined with stop/interrupt (HIGH) [verified]

`cmb_process_wait_event` registers the caller in two places — on the event's waiter list and on its own awaitables list — and relies entirely on `wakeup_event_event` (the SUCCESS/CANCELLED delivery path) to remove them. If the process is resumed by anything else, typically its timeout timer, **both registrations survive**. Two demonstrated consequences:

*Repro (`repro_b_event_wait.c`, part 1):* P waits for an event scheduled at t=10 with a 5-unit timeout. The timeout returns correctly at t=5; when the event fires at t=10, the stale waiter registration schedules a SUCCESS wakeup that **resumes P inside an unrelated 100-unit hold, ending it after 5 units with signal SUCCESS**. Silent in release and debug builds alike.

*Repro (part 2):* Q waits for event F at t=20 (no timer this time); a user event at the same timestamp, ordered after F, calls `cmb_process_stop(Q)`. F fires first; the stop then runs `cmi_process_cancel_awaiteds`, whose EVENT branch calls `cmi_event_remove_waiter`, which **release-asserts that the event is still enqueued** — it is not — and the whole program **aborts (SIGABRT) in the default release build**:

```
20.000  dispatcher  cmi_event_remove_waiter (557):  Fatal: Assert "cmi_hashheap_is_enqueued(event_queue, key)" failed
```

The window is any same-timestamp ordering that runs a stop/interrupt of a waiter between its awaited event firing and its wakeup executing — a perfectly ordinary occurrence in models that tear processes down on completion signals. (With `-DNASSERT` the abort becomes a lookup on a missing key instead, i.e. undefined behavior via the `cmi_hashheap_item` release assert being compiled out.)

**Fix:** (a) make `cmi_event_remove_waiter` (and `cmi_event_add_waiter`'s precondition) tolerant of an event that has already left the queue — return false rather than assert, matching the stated philosophy in `cmi_process_cancel_awaiteds` that "state could be momentarily inconsistent while cleaning out the queues"; (b) on any non-SUCCESS, non-CANCELLED return from `cmb_process_wait_event`, deregister from the event's waiter list (if the event is still scheduled) and remove the EVENT awaitable. The generation-counter mechanism below subsumes the spurious-wakeup half of this.

### R3 — `cmb_process_wait_process` leaves its waiter tag behind on a timeout: spurious wakeup when the awaited process later finishes (MEDIUM-HIGH) [verified]

Same shape, third primitive. *Repro (`repro_c_wait_process.c`):* W waits for long-running process L with a 5-unit timeout; the timeout returns correctly at t=5; when L finishes at t=10, `wake_process_waiters` finds W's stale tag and **resumes W inside an unrelated 100-unit hold, ending it after 5 units with signal SUCCESS**. The stale tag also means `wakeup_event_process` strips whatever PROCESS awaitable W has at that moment (it removes by type with a NULL wildcard), so if W were by then waiting on a *different* process, that wait's bookkeeping is silently destroyed too.

**Fix:** on a foreign resume, remove the waiter tag from the awaited process (`cmi_process_remove_waiter`) and the PROCESS awaitable; or the generation counter below.

### Common root cause and the recommended unifying fix

R1–R3 (and the analogous latent case in `cmb_condition`, whose `wakeup_event_condition` also strips the first RESOURCE awaitable by wildcard before resuming — see R7) share one root cause: **wakeup events are fire-and-forget**. The June fixes taught the *initiators* of process teardown (interrupt, stop, exit, preempt) to pattern-cancel pending wakeups, which is why those paths are now clean. But a process that leaves a wait *on its own* — timeout, `cmb_process_resume` from user code, a condition broadcast racing a grant — cancels nothing, and no wakeup handler can tell a fresh wakeup from a stale one.

Rather than adding a fourth and fifth spot repair to the existing three, I recommend making staleness *detectable*:

1. Add a `uint64_t wait_generation` to `struct cmb_process`, incremented every time a wait primitive returns to its caller (equivalently: every time the process is resumed and accepts the signal).
2. Every internal wakeup scheduler stamps the target's current generation into the event (the event payload has a spare fourth slot at the `cmi_hashheap_enqueue` level; an internal `cmi_wakeup_schedule` helper would keep `cmb_event_schedule`'s public 3-argument shape).
3. Every wakeup handler compares generations and **discards stale wakeups**; a discarded *resource grant* additionally re-signals its guard so the grant is re-offered (the wakeup must carry the guard pointer for this, which it can, in the same spare slot arrangement).

This single mechanism enforces the invariant "a wakeup may only resume the wait it was issued for" everywhere at once, including in user-composed patterns nobody has thought of yet, at the cost of one integer compare per wakeup. The per-primitive repairs listed under R1/R2/R3 are the minimal alternative; they fix the demonstrated cases but leave the invariant unenforced. Either way, `cmi_event_remove_waiter` tolerance (R2a) and the guard re-signal on abandoned/removed grants (R1) are needed independently.

**Regression tests to add with the fix** — this family is invisible to golden-file tests unless the timestamps tie, so make them tie deliberately: a matrix over {resource, pool, buffer, objectqueue, condition, wait_event, wait_process} × {timeout, cancel, interrupt, stop, resume} with the out-of-band resume scheduled at exactly the grant/fire timestamp, asserting (a) no wait ever returns a signal it wasn't issued, (b) hold durations are exact, (c) no waiter remains queued at a free resource after the queue drains, and (d) conservation of pool units and single-holder invariants. Repros A–C can seed this directly.

## Medium-severity findings

**R4 — `cmb_logger_error` outside a worker thread terminates the process with exit status 0 [verified].** In single-threaded use (tutorials 1–2 style, no `cimba_run`), the unarmed-recovery branch falls back to `pthread_exit(NULL)` from the main thread; with no other threads the process then exits **successfully** as far as any shell, script, or CI harness can tell. Demonstrated: a two-line model calling `cmb_logger_error` exits with status 0. An error path that reports success is a trap for exactly the batch/scripted workflows an OR library lives in. Suggest `exit(EXIT_FAILURE)` (or `abort()`, matching `cmb_logger_fatal`) when recovery is unarmed, and documenting the difference between error-in-trial (trial abandoned, run continues) and error-outside-trial (process ends).

**R5 — Exported-symbol namespace pollution [verified].** `nm -D` on `libcimba.so` shows ten defined globals outside the `cmb_`/`cmi_`/`cimba_` namespaces: `coroutine_main`, `coroutine_current`, `coroutine_pool`, `static_pools`, `objectqueue_tags`, `observer_tagpool`, `cmg_atexit_armed`, `wake_event_waiters`, `wakeup_event_resource`, `wakeup_event_preempt`. In C there is one flat link namespace; an application (or another library — think of a COIN-OR solver stack linking half a dozen packages) defining its own `coroutine_main` or `static_pools` will silently interpose or collide. These are cross-TU "friend" symbols and thread-locals that cannot be `static`, so rename them with the `cmi_` prefix; longer-term, build with `-fvisibility=hidden` plus explicit export attributes (or a version script) so only the intended API is visible at all. Cheap now, breaking later.

**R6 — `cmb_event_cancel` (and `reschedule`/`reprioritize`) release-assert a non-empty queue before their graceful not-found path [by inspection].** `cmb_assert_release(cmi_hashheap_count(event_queue) > 0u)` precedes the `is_enqueued` check that is documented to return false for an already-fired handle. Cancelling a stale handle — the normal, documented thing to do with a timer that may have fired — **aborts** if the queue happens to be empty at that moment (e.g. end-of-run cleanup code cancelling leftover timers after the last event). Delete the count assert and let the not-found path answer; it is the whole point of that path.

**R7 — Inconsistent wakeup handlers for guard waits [by inspection].** `wakeup_event_condition` removes the waiter's first RESOURCE awaitable (NULL wildcard) *before* resuming; `wakeup_event_resource` removes nothing and lets `cmb_resourceguard_wait` clean up after resume. Both currently work because a process can only be inside one guard wait at a time — but only as long as no stale condition wakeup exists (R1 class): a stale `wakeup_event_condition` will strip the awaitable of whatever guard the process is *currently* waiting on, orphaning that queue entry beyond the reach of `priority_set`/`cancel_awaiteds` and re-opening an F1-style lost-wakeup. Unify on the resource-handler convention (handler resumes, wait cleans up) as part of the R1–R3 fix.

## Low-severity and polish items

(a) **Test-suite leak hygiene [verified]:** with LeakSanitizer active, `test_condition` fails on five test-teardown leaks (two processes, a hashheap, an slist, and an indirect grow allocation never destroyed by the test); the June 18 review noted the same in `test_data`. CI masks this with `detect_leaks=0`. The *library's* destroy paths are what leak checking would actually certify for a COIN-OR audience — make the tests leak-clean and flip one ASan CI job to `detect_leaks=1`. (b) **Self-preemption:** `cmb_resource_preempt` with `victim == caller` cancels the caller's own timers and schedules a self-targeted PREEMPTED wakeup that will land spuriously later; assert `victim != cmb_process_current()`. (c) `cmb_process_hold`'s foreign-wakeup branch calls `cmb_process_timer_cancel` and then redundantly `cmi_process_remove_awaitable` for the same handle (timer_cancel already removed it); harmless, but tidy it. (d) `cmb_process_timer_add`'s comment ("Returns CMB_PROCESS_TIMEOUT when returning normally...") describes the old hold-with-timeout semantics, not this function. (e) `wakeup_event_time` is the one wakeup handler that still hard-asserts `RUNNING` instead of check-and-warn; unreachable with a dead target through current library paths, but brittle against the next refactor — align it with its four siblings. (f) `cmb_resource_terminate` with waiters still queued signals the guard mid-teardown, scheduling wakeups into a dying object; assert the guard queue empty on terminate, or document the precondition. (g) `cmb_resource_release` verifies `holder == pp` only in debug; in release, a buggy model releasing a resource it doesn't hold silently evicts the true holder — this one deserves to be a release assert given the library's argument-checking philosophy. (h) The per-thread stack pool never returns memory before thread exit (high-water cache) and recycles only within the owning thread; both are sound engineering choices for this design, but worth one sentence each in the documentation. (i) `cimba_threads_use` mutates a shared global unsynchronized with a concurrent `cimba_run`; fine under the documented single-owner model, worth a doc note.

## Strengths

Beyond the fix quality already covered, several things in this snapshot deserve explicit credit. **The new stack allocator** is a textbook solution to the measured `mprotect` serialization: per-thread segregated free lists keyed by rounded size, guard pages left `PROT_NONE` across recycling so the syscall is paid once per fresh stack ever, unprotect deferred to thread cleanup, and the free-list link stored in the first usable word above the guard page where live stacks never conflict with it. I read it looking for trouble and found none. **The install story** went from broken (June 10) to exemplary: staged-install verification in CI, pkg-config, a documented rationale for each installed internal header, and headers that genuinely compile at C11 for consumers. **The CI matrix** — release/debug asserts semantics tests, ASan, UBSan, TSan with documented signal-handler options, Windows MinGW, and the install job — is well beyond peer libraries. **The assert framework printing the RNG seed** in every failure message is a small touch with outsized value for stochastic-bug reproduction. And the **comment culture** remains excellent: the CET note in the assembly, the `__builtin_setjmp` rationale, and the compaction explanation each capture a hard-won lesson precisely where the next maintainer will need it.

## Performance

Not re-benchmarked in this single-core container. Architecturally, the three performance concerns from earlier reviews are all resolved: `mprotect` off the steady-state path (stack pool), `pushfq`/`popfq` removed from the context switch, and hash-map tombstone decay bounded by compaction. One observation for the roadmap rather than the release: the guard and event hash-heaps, the mempools, and the stack pool all cache at high-water; long-running server-style workloads with a large transient spike will hold that footprint until thread exit. That is a documented-behavior matter, not a defect.

## Tests and CI

The suite is strong on per-module behavior and now covers most of the June regressions (the assert-semantics matrix, the guard reprioritize/stop tests, the weighted-summary pin, the stochastic M/G/1 end-to-end). The gap this review exposes is precisely the one its predecessors warned about in general terms: **tied-timestamp interactions between independent wakeup sources are exercised nowhere**, and `test_resourceguard.c` itself uses the vulnerable timer-then-acquire idiom with timestamps that happen never to collide. The regression matrix proposed under R1–R3 is the single highest-value test investment before 3.0. Second: make the tests leak-clean and enable leak detection in one CI job. Third (carried over): a small resource-contention test running *inside* `cimba_run` workers, so the fiber resume path under contention is sanitizer-covered.

## Prioritized recommendations before an official 3.0

1. **Close the stale-wakeup class (R1, R2, R3, R7)** — preferably with the wait-generation mechanism, plus the guard re-signal on abandoned/removed grants and a tolerant `cmi_event_remove_waiter` — and land the tied-timestamp regression matrix with it. This is the release gate: the affected idiom is one the library's own tests teach, the failures are silent under every sanitizer, and the consequences (spurious signals, corrupted timing, stranded waiters, release-build aborts) strike exactly the models that would choose Cimba for serious work.
2. Fix the event-API empty-queue asserts (R6) and the exit-status-0 error path (R4).
3. Rename the ten unprefixed exports and adopt hidden visibility (R5) — do this before 3.0 while it breaks nobody.
4. Leak-clean the test suite and turn leak detection on in one CI job; sweep the polish list (a)–(i).
5. Document the timeout idiom (once fixed), tied-timestamp ordering semantics, and the stack-pool retention behavior — the background documentation's quality deserves matching coverage of these operational corners.

## Verification statement

On Linux x86-64 with GCC 13.3, I verified by building and executing the code that this snapshot builds warning-clean at `warning_level=3` in release and debug+ASan/UBSan configurations; that the complete shipped test suite passes in release (23/23); that the per-module unit tests are ASan+UBSan-clean apart from the documented test-teardown leaks; and that the staged install is self-contained, with every public header compiling standalone out-of-tree in C11 mode and a correct pkg-config file. I re-checked all eighteen previously reported defects (F1–F7, M1–M8, N1–N4) plus the residual items from the interim reviews and found every one fixed in this tree, several with structural improvements.

I also demonstrated, with three minimal reproduction programs run against both the default release build and the full debug+sanitizer build, the new defect family R1–R3: stale wakeup events from the resource-guard, event-wait, and process-wait machinery that spuriously resume processes after a timeout at a tied timestamp, corrupt subsequent timer-based waits, strand a queued waiter at a free resource indefinitely, and — via a registration-cleanup gap — abort the process with a release assert when a stop coincides with the awaited event's firing. A fourth program demonstrated the exit-status-0 error path (R4). The reproduction programs accompany this document.

Assessment: the fix campaign since June has been thorough and verifiably effective, and the engine, data structures, numerics, packaging, and CI are at or above the bar for the library's stated ambitions. The remaining barrier to calling this a release candidate is the stale-wakeup family, which sits in supported, documented, test-demonstrated usage patterns and fails silently. It is one focused fix with a clear design (the generation counter), and the codebase's own history — every prior finding closed, most of them structurally — is good evidence it will be closed well. With R1–R3/R7 fixed and the tied-timestamp regression matrix in place, I see no structural obstacle between this snapshot and a trustworthy 3.0.
